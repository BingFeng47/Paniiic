# Submission helper

Run with `/submission` when preparing the Devpost entry.

1. Read `docs/submission-checklist.md` and report every unchecked item, with what is needed to
   finish it.
2. Read `docs/kiro-log.md`, the specs in `.kiro/specs/`, the hooks in `.kiro/hooks/`, the steering
   files and the MCP config. Draft the **"How we used Kiro"** writeup in `docs/kiro-writeup.md`,
   answering each question Devpost asks:
   - Which Kiro surfaces we used (IDE, CLI, Web, Crew) and how they differed.
   - Custom agents we built or used, and how they helped.
   - Which tasks the agent hooks automated and how that changed the workflow.
   - How we structured specs for Kiro to implement, and how that compared with vibe coding.
   - How steering improved Kiro's responses, and which approach worked best.
   - How MCP extended Kiro, and what would have been hard without it.
   - Whether property-based tests caught issues unit tests would have missed, and for which
     requirements.
   - Which Kiro powers we used, if any.
3. Use concrete examples with file paths and numbers. Do not claim anything the repo cannot show.
4. Write in plain English. Everything submitted must be in English.
